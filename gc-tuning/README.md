# GC Tuning — Issue #9

> Sweep the histogram-equalization benchmark under four garbage collectors,
> capture pause-time evidence, and pick the one that best matches the
> workload. Required by PDF section 6 *"Garbage Collector Tuning"*.

## TL;DR

**Recommended collector: G1** (`-XX:+UseG1GC`) — On the test environment
it's the win on every dimension we measured, by a comfortable margin:

| GC       | Σ avg-ms | Σ GC time (ms) | GC count | GC / work |
|----------|---------:|---------------:|---------:|----------:|
| **g1**   |   425.02 |             16 |        2 |     0.38% |
| parallel |   427.23 |            133 |       38 |     3.11% |
| serial   |   447.56 |            345 |       38 |     7.71% |
| zgc      |   530.19 |            616 |      145 |    11.62% |

Source data: `gc-tuning/comparison.md`, generated by
`pt.isep.sismd.histogram.GcComparisonReport`.

## 1. Test environment

| Field | Value |
|---|---|
| JDK | OpenJDK 26.0.1+8-34 (Server VM, mixed mode) |
| OS | Windows |
| Cores | 24 logical |
| Heap | `-Xms2g (fixed, identical across all four runs) |
| Sweep matrix | 5 implementations × 3 image sizes × {1, 2, 4, 8, 16, 24} threads × 13 iterations (3 warm-up + 10 measured) → 75 configs per GC |

## 2. Methodology

The Issue #8 benchmark harness (`BenchmarkRunner`) emits three CSVs per run.
For Issue #9 we run that same harness four times — once per GC — into
separate sub-directories of `results/`, and capture a `-Xlog:gc*` log
per run as raw evidence of pause behaviour.

| GC | Flag | Family |
|---|---|---|
| Serial   | `-XX:+UseSerialGC`   | Single-threaded, stop-the-world |
| Parallel | `-XX:+UseParallelGC` | Multi-threaded throughput collector |
| G1       | `-XX:+UseG1GC`       | Region-based, pause-time-targeted, default since JDK 9 |
| ZGC      | `-XX:+UseZGC`        | Concurrent, sub-millisecond pauses |


## 3. Running the sweep

Run from the **project root**, after `mvn -q compile`.

### Windows / PowerShell

```powershell
gc-tuning\run_all.ps1                  # all four, then aggregate
gc-tuning\run_g1_gc.ps1                # one at a time
gc-tuning\run_all.ps1 -HeapMB 4096     # custom heap
```

### Linux / macOS

```bash
bash gc-tuning/run_all.sh
HEAP_MB=4096 bash gc-tuning/run_all.sh
```

Each script writes:

- `results/<gc>/results_time.csv`, `results_memory.csv`, `results_gc.csv`
- `gc-tuning/logs/<gc>.log` — full unified GC log
  (`-Xlog:gc*:utctime,level,tags`)

Then `pt.isep.sismd.histogram.GcComparisonReport` merges all four trees
into `gc-tuning/comparison.md`.

## 4. Analysis

### G1 wins on throughput

`g1` finished the entire sweep in `425.02 ms` of summed work time, with
`parallel` 0.5 % behind, `serial` 5 % behind, and `zgc` 25 % behind.
For mixed thread counts and short-lived allocations, G1's region-based
young-gen layout is exactly what this workload wants — the JDK 9+
default for good reason.

### G1 wins on pause time too — by an order of magnitude

This is the headline result:

```
g1:        2 GC events,  16 ms total
parallel: 38 GC events, 133 ms total
serial:   38 GC events, 345 ms total
zgc:     145 GC events, 616 ms total
```

G1's "string pulled tight" prediction model collected **only twice** in
the entire 24 GB mean allocation sweep, because most allocations died inside the eden region before any collection had to happen. Parallel and Serial each performed 38 collections (≈ one per gigabyte of allocation), as classical generational collectors do.

### Why ZGC underperforms here — counterintuitive but well-known

ZGC is designed and optimised for workloads characterised by very large heaps (multi-terabyte scale) and strict latency requirements, with marketing claims focusing on sub-millisecond pause times. However, in the context of a 2 GB heap with a small live set, this benchmark falls outside its intended operating regime.

- ZGC executed **145 garbage collection cycles**, reflecting its concurrent design, which proactively triggers collections to maintain short pause times.
- Each cycle incurs **load-barrier overhead on every reference access**, as ZGC relies on colored object pointers and load barriers to maintain concurrent correctness.
- This overhead is borne primarily by application threads rather than being accounted for as explicit GC pause time, leading to increased measured application latency (`avgMs`) rather than elevated `gcTimeMs`.

Consequently, the aggregated execution time (`Σ avg-ms = 530.19 ms`) is approximately 25% worse than G1, despite ZGC maintaining lower individual pause durations.

ZGC would be expected to demonstrate superior performance in environments with significantly larger heaps (e.g., ≥32 GB), high object retention, and stringent tail-latency constraints. Under the present workload characteristics, it is operating outside its optimal design envelope.
